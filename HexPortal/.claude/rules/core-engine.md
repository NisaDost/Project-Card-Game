# Core engine rules

- **Pure C#.** No `UnityEngine` or `UnityEditor`. Target C# 9 and netstandard2.1, with no `record` and no `init`. The asmdef has `"noEngineReferences": true`.
- **Deterministic.** Use one RNG class (`Rng`, xorshift or PCG) seeded from the match seed and stored in `GameState`. Never use `System.Random`, `DateTime.Now`, `Guid.NewGuid`, or unordered `Dictionary`/`HashSet` iteration where order affects the outcome.
- **Commands in, events out.** State changes only through `Engine.Apply(GameState, ICommand)`, which validates the command, mutates the state and returns a list of `GameEvent`. The Unity client and the AI never mutate state directly.
- **Legal moves are generated by the engine.** `Engine.GetLegalCommands(state, player)` is the single place that decides legality. The UI highlights and the AI both use it.
- **Hidden information.** `PlayerView.For(state, player)` returns a redacted copy: no opponent hand, quests, passive, traps or pool order, and the board is filtered by fog of war (GDD §11): `Hidden` cells carry no data, `Explored` cells carry the player's last-seen snapshot, only `Visible` cells carry live data. The AI receives a `PlayerView` only.
- **No leaks through legality or events.** `GetLegalCommands` for a player may only depend on what that player can see (U-12, V-07): e.g. a move is never rejected because of a hidden unit. Events returned to a player are filtered the same way (an unseen enemy move produces no event for that player).
- **Two resources.** `Mana` (card costs, T-01…T-03, T-07) and `Energy` (unit actions, T-05) are separate fields with separate rules. Never merge them.
- **Off-turn triggers.** Tower shots (U-27) and overwatch (U-28) resolve inside `Engine.Apply` of the opponent's command, in the order given by U-29. They are not separate player commands.
- **Data lives in `Core/Data/Catalog.cs`.** Card, unit, quest, passive and event definitions are plain static readonly data. Numbers never appear anywhere else, so logic reads `Catalog`.
- **Effects** are a small `switch` over an `EffectKind` enum. Do not build a scripting system.
- **Tests:**
  - NUnit, in `Tools/Engine.Tests`, one fixture per GDD section (`BoardTests`, `UnitTests`, `CardTests`, ...).
  - The test name starts with the rule ID.
  - Use a `TestBoard` builder to place units and set up exact scenarios. Do not rely on random maps in rule tests.
  - Add a replay test: seed + command list → the same final state hash.
  - Add fog leak tests: for a scripted match, nothing in `PlayerView.For(state, p)` or in p's events reveals an enemy unit that p cannot see.
- Keep files small and obvious: `GameState`, `Engine`, `Rules/*.cs` (one per GDD section, incl. `Rules/Visibility.cs`), `Hex/*.cs`, `Ai/GreedyAi.cs`, `Data/Catalog.cs`.
